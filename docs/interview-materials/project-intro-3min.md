# 3~5 分钟项目介绍（面试口播版）

> 适用：Java/后端 + RAG 方向岗位自我介绍 / 项目深挖开场。
> 对应项目：RAG 知识库 · Java 程序员智能面试助手（Interview RAG）。

---

## 一、一句话定位

我做的是一款**基于 RAG（检索增强生成）的 Java/后端技术面试陪练与问答系统**：用户上传个人知识库（Markdown / PDF / Word），系统通过「查询改写 → 混合检索 → 重排 → LLM 生成」流水线作答，并能多轮**模拟真实面试**（出题、答题评价、按用户隔离、生成报告）。

## 二、为什么做它 / 背景

面试准备最大的痛点：知识库内容很全，但**检索质量没人管**——是否命中、命中了靠不靠前，此前完全靠拍脑袋。我把它当作一个「检索质量工程化」的课题来做：不满足于"能跑通 RAG"，而是把检索做成**可评测、可优化、可复用**的工程底座。

## 三、技术栈（一句话带过）

FastAPI 后端 + 阿里云百炼 `qwen-turbo` 生成 + 硅基流动 Embedding/Rerank + FAISS 向量库（混合 rank_bm25/Whoosh/SQLite FTS 稀疏检索）+ Redis 会话 + SQLite 长期持久化 + SSE 流式。前端原生 HTML/JS 单页。

## 四、我做的最重要的两件事（讲深亮点）

### 1. 用「消融实验」把检索质量由玄学变成可优化（Part A）
- 痛点：全开关常开，换什么都没依据。
- 做法：建立**评测集 → 基线 → 门禁 → 消融**闭环。手写 120 条含四类难题（跨文档推理 / 易混辨析 / 口语面试 / 边界反直觉）的评测集；对 `query rewrite` 和 `rerank` 两个开关做 4 组开关开/关消融。
- 结论：**rerank 贡献最大**（recall +0.063）、query rewrite 也正向；但两者同开会把 MRR 从 0.829 拉到 0.798——识别出这是**排序问题而非召回问题**，据此决定保留 `qr_on+rr_on` 并留待参数优化。
- 价值：说明我会用**数据做技术取舍**，而不只是"加个开关"。

### 2. 用「统一检索门面」消除问答与面试两套检索的割裂（Part B）
- 痛点：问答走完整管线，面试却只走一条 raw FAISS 稠密检索的"独木桥"，检索质量裸奔且不可复用。
- 做法：抽出 `RetrievalFacade`（`qr→hybrid→rerank→parent`），问答与面试**复用同一套已验证管线**，管线上做策略差异（面试评价用「问题+回答」拼接检索）。
- 落地要点：**面试追问默认不触发检索**（控制成本）；出题/评价都**带来源溯源**；检索失败优雅降级不阻塞面试。
- 结果：面试子集 17 条复试，MRR 从 0.559 提到 0.588、recall 不降，**pytest 143 全绿**。
- 价值：体现**抽象能力**（抽公共底座）与**成本意识**（追问不检索）。

## 五、工程化的几个细节（体现严谨，被追问时展开）

- **缓存红线**：响应缓存 key 只基于原始问题（去掉 session_id/消息轮次），命中率从近 0 修到可命中；面试评价 query 含用户回答，**绝不进缓存**。
- **降级链**：Redis 挂→禁缓存；BM25 缺失→退 FAISS-only；重排失败→不影响面试出题。
- **流式稳定**：SSE 在多会话切换/删除时不断流、不 abort、不写错会话；token 渲染做了节流。
- **安全**：Markdown 渲染过 DOMPurify，防 XSS。
- **全栈用户隔离 + JWT 认证 + 限流**。

## 六、一句话收尾 / 亮点强调

> 这个项目最打动人的不是"接了个 LLM"，而是我把它当成**一个可评测、可优化的系统**在工程化：有评测闭环定基线、有消融实验驱动决策、有统一检索底座复用、有明确的成本与安全约束。面试若追问，我最想讲的是**消融实验那条**——因为它体现我用证据而不是感觉做技术选择。

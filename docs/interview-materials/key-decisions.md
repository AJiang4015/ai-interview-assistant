# 关键技术决策说明（面试深挖 Q&A）

> 用途：面试被追问"为什么这么设计 / 有没有权衡"时的弹药库。
> 每条给出：决策事项 → 取舍 → 依据（对应 DECISIONS.md DR 编号）。

---

## 1. 为什么统一检索门面 RetrievalFacade？为什么是这个位置？

- **决策**：抽取 `RetrievalFacade`，让问答与面试共用 `qr→hybrid→rerank→parent` 一条管线。
- **取舍**：代价是重构 `rag_service`（行为等价收口）；收益是把"最好的检索能力"复用到全部业务，消灭面试 raw FAISS 独木桥，且检索优化一次、受益所有业务。
- **为什么放服务层**：它依赖 Hybrid/Rerank/Embedding 等，属于业务编排；放服务层符合"API 薄、服务层持有管线决策"的分层。
- **依据**：Part B spec；DR-001（降级）、DR-003（rerank 选型）、DR-004（缓存红线）、DR-005（SSE 稳定）。

## 2. 为什么用消融实验决定 query rewrite / rerank 去留（Part A）？

- **决策**：不做"拍脑袋开关"，而是 `评测集 → 基线 → 门禁 → 消融`。
- **取舍**：成本是要跑 4 组真实 LLM 评测（手写集 40 条控成本）；收益是**用数据说话**——最终发现 rerank 贡献最大(+0.063)、query rewrite也正向、但两者同开会把 MRR 从 0.829 拉到 0.798。
- **为什么同开 MRR 反降**：rewrite 改写语义拉广召回（recall↑），但 rerank 把语义相似的次要文档顶前、主文档后移（mrr↓），且根因集中在跨文档多源题。
- **结论处理**：保留 `qr_on+rr_on` 全开（关任何开关都掉召回），把 mrr 回落记为**排序参数优化项**而非开关项。
- **依据**：Part A spec §7；DR-004 类"先证据后决策"纪律（PROCESS §0）。

## 3. 为什么缓存 key 只基于原始问题？（DR-004 / P001）

- **决策**：响应缓存 key = 原始问题原文哈希，去掉 `session_id`、`msg_count` 等可变维度。
- **原因**：旧实现混入这两个维度，导致同一问题跨会话/轮次永不命中，命中率≈0；去掉后相同问题可跨会话复用（TTL 1h 防陈旧）。
- **临界**：面试评价 query 含用户回答，**绝不进缓存**（含回答的 key 会泄漏个性化/稳态变，且命中无意义）。
- **依据**：PROBLEM.md P001；PROCESS 门禁 Door 5。

## 4. 为什么重排用远程 API 而非本地模型？（DR-003）

- **决策**：重排走硅基流动 `Qwen/Qwen3-Reranker-4B` API，标题弃用本地 `BAAI/bge-reranker-v2-m3`。
- **原因（两个失败证据）**：① 本地 bge 加载触发 OMP 动态库冲突导致进程崩溃；② 国内网络下载 HuggingFace 模型失败。
- **取舍**：远程 API 有延迟/成本，但稳定可落地、免本地资源雷区。
- **依据**：PROBLEM.md P003/P004；DR-003（环境影响，验证过的选择）。

## 5. 为什么 SSE 而不是 WebSocket？为什么流式这么稳？（DR-005）

- **决策**：SSE（单向事件流）足以满足"服务端→前端"的流式推送，事件为 `session/retrieval/token/done/error`。
- **取舍**：WebSocket 双向能力强但复杂度高；本场景只需要单向，SSE 更简单、可自动重连，故选 SSE。
- **稳定性设计**：流式绑定到发起时的会话 ID；会话切换/删除不 `abort()`，让流自然完成写回；token 渲染节流（rAF+pendingRender）减少重绘。
- **依据**：PROBLEM.md P002 + D1~D4/D11；DR-005。

## 6. 为什么"追问默认不检索"？（成本 / 语义）

- **决策**：面试追问环节（最多 5 层）默认不触发真实检索，只出题与评价各检索一次（单场调用≈题目数×2）。
- **取舍**：牺牲追问时可能更准的上下文；控制每场的 API 调用/延迟/成本；用开关 `enable_interview_followup_retrieval` 供实验放开。
- **依据**：Part B spec §5.2。

## 7. 为什么索引/落盘假定单 worker？（DR-002 / D9）

- **决策**：FAISS 与 ingest state 落盘按单进程设计，`--workers 1` 启动。
- **原因**：多项状态（FAISS 内存索引、BM25、ingest_state.json）非进程级安全，多 worker 并发写会不一致。
- **取舍**：牺牲多进程横向扩展，换取落盘/索引一致性；部署用 Docker 单实例。
- **依据**：DR-002；PROBLEM P006。

## 8. 为什么混合检索用 RRF 融合 + parent 扩展？

- **决策**：稠密(FAISS) + 稀疏(BM25/SQLite FTS) 用 **RRF（Reciprocal Rank Fusion, k=60）** 融合到 top-20，再 parent-child 上下文扩展 + 去重，最后重排精排 top-5。
- **取舍**：RRF 无需调权重（纯排名融合，鲁棒），兼顾稠密语义与稀疏精确词；parent 扩展补偿"切块切断了上下文"。
- **依据**：Part A 大规模 RAG 检索升级（`docs/superpowers/specs/2026-08-16-large-scale-rag-design.md`）。

## 9. 全栈用户隔离 + 认证怎么做的？

- **决策**：passlib[bcrypt] 哈希 + PyJWT；`get_current_user` 依赖注入；会话/面试记录按 `username` 隔离；Redis + SQLite 双存与会话归属校验。
- **取舍**：登录态下多用户互不可见/不可越权（面试场次归属校验），代价是有鉴权开销。
- **依据**：`d2ace2f` / `dfd1a88`（用户隔离、认证加固）。

## 一句话总结要传递的"工程心智"

> 我不是"接好一个 LLM 就完事"，而是把 RAG/检索当成**可评测、可复用、有成本与安全约束的工程系统**：用消融产出决策依据，用统一底座复用能力，用降级与缓存红线控制稳健性，用评测集守住"优化不回退"。

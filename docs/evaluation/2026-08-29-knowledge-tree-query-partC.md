# 为何暂缓「知识树 query」优化（面试深挖 Q&A）

> 背景：Part B 把面试检索迁移到统一 `RetrievalFacade` 后，「出题 query 由知识点树驱动」与「Java 集合主题召回不足」都被识别出来，但**刻意不并入 Part B**。

---

## 为什么要做知识树 query？（它要解决什么）

- Part B 复用统一底座后，`_generate_question` 的出题检索词仍是 `f"{position} 技术面试题 {difficulty}"` 这类"填空式"query。
- 更理想的是：**先定位考点，再检索考点内容**。项目已有 `TopicTracker` 能从知识点树（如 `Java后端.json`）拿到 `get_next_suggestion()` → `{topic, category, reason}`，能告诉你"下一轮该考哪个考点"。
- 若用 `建议考点 + 其 knowledge_points` 去构造检索 query，可让出题真正命中知识库对应文档，改善召回（尤其"Java 集合"类被串题的场景）。

## 为什么这次没做？（范围控制，工程纪律）

1. **Part B 的目标是"统一检索底座"**，不是"提升出题 query 质量"。前者是基础设施修复（消除双链路割裂），后者是业务效果优化。混在一起会**双线并行、难以归因**——万一指标变了，分不清是底座还是 query 变化导致。
2. **依赖前提未收敛**：知识树 query 的好坏还依赖知识树本身的质量 / 检索表征；在底座稳定前先改 query，属"没修好底座先堆业务"，违背"先修好底座再迁移核心卖点（不插队）"的既有纪律（Part B spec §2 明确写了这条）。
3. **避免范围蔓延**：当前复试已经证明「面试检索不劣于升级前 + MRR 微升」，Part B 目标达成、可收尾。再塞新特性会让验收、复盘、面试表达都变得不聚焦。
4. **它单独值得一个完整的优化闭环**：涉及建树标准、query 构造策略、独立评测（`.eval_interview` 子集仍可用）、以及可能的重排序参数调优——这本身就是一个小迭代，宜单独立项。

## 决策结论

- **Part B = 统一检索底座（已完成、已验收）**。
- **知识树 query = 单列 Part C**，作为"在已统一底座之上，进一步提升面试出题召回"的后续优化项，**不并入 Part B**，避免该阶段范围扩大、成果不聚焦。

## 被追问时的一句话

> "面试链路触达知识库的通道已经归一（RetrievalFacade），但'到底出哪道题的考点、用考点去检索'这件事，和'底座是否统一'是两件独立的事。我选择先收敛前者并验收，再把'考点驱动的出题 query'作为独立迭代 Part C 来做，这样才能分清楚每个改动对指标的真实贡献。"

# Part C：知识树驱动 query 检索优化（后续优化项登记）

> 状态：**规划（待立项）**  关联：Part B 遗留问题（Java 集合主题召回不足）

## 目标
在统一 `RetrievalFacade` 之上，把面试**出题 query** 从填空式（`f"{position} 技术面试题 {difficulty}"`）改为**知识点树驱动**（先用 `TopicTracker` 定位应考考点，再用考点及其 `knowledge_points` 构造检索词），提升面试出题的检索命中与针对性。

## 拟解决
- Java 集合类题目（ConcurrentHashMap / ArrayList&LinkedList / HashMap 线程安全）在复试中 top-5 未命中 `JAVA集合.md`，被 `test_java/Redis.md` 串题。
- 出题检索词语义与知识库措辞错位。

## 拟做（立项后细化）
1. 明确 `TopicTracker` 输出"应考考点 + knowledge_points"的手段；
2. 定义"考点 → 检索 query"构造策略；
3. 用现有 `data/eval_interview_subset.json` 做该策略的独立消融/对照；
4. 若涉及重排参数（RRF k / rerank top_k / query rewrite 规则）一并纳入，复用 Part A 消融方法。

## 不做（避免蔓延）
- 不新增技术栈、不改统一底座结构、不影响问答链路。
- 出题/评价的触发策略（追问不检索）保持不变。

## 启动条件
- 需先确认知识树"查询词输出能力"成熟（Part B 前置条件 §2 的验证项），再据此决定走完整 query 改造或仅参数调优。

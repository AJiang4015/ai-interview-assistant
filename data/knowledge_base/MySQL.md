# MySQL 事务 

## 事务特性

**ACID：**

- **原子性（Atomicity）**：一个事务中的所有操作，要么全部完成，要么全部不完成，不会结束在中间某个环节，而且事务在执行过程中发生错误，会被回滚到事务开始前的状态，就像这个事务从来没有执行过一样。
- **一致性（Consistency）**：是指事务操作前和操作后，数据满足完整性约束，数据库保持一致性状态。
- **隔离性(Isolation）**：数据库允许多个并发事务同时对其数据进行读写和修改的能力，隔离性可以防止多个事务并发执行时由于交叉执行而导致数据的不一致，因为多个事务同时使用相同的数据时，不会相互干扰，每个事务都有一个完整的数据空间，对其他并发事务是隔离的。
- **持久性(Durability）**：事务处理结束后，对数据的修改就是永久的，即便系统故障也不会丢失。

InnoDB 引擎通过什么技术保证事务的四个特性：

- 持久性是通过redolog（重做日志）来保证的；
- 原子性是通过undolog（回滚日志）来保证的；
- 隔离性是通过MVCC（多版本并发控制）或锁机制来保证的；
- 一致性则是通过持久性+原子性+隔离性来保证；

## 并行事务会引发什么问题？

**脏读、不可重复读、幻读**。

### 脏读

如果一个事务「读到」了另一个「**未提交事务修改过的数据**」，就意味着发生了「脏读」现象。

![img](https://cdn.nlark.com/yuque/0/2025/webp/53862437/1749799877111-bf5081f9-72cc-4a3f-bc5f-c4ecc500dcac.webp)

### 不可重复读

**不可重复读** 发生在同一个事务内。当事务A第一次读取某一行数据（比如 `**id=1**` 的余额）后，事务B **更新**了这行数据并提交，事务A再次读取同一行时，发现数据值变了（比如余额从100变成50了）。它关注的是**同一行数据值的变化**。

![img](https://cdn.nlark.com/yuque/0/2025/webp/53862437/1749799936129-6055887f-d177-40a7-8020-a5375d98a19b.webp)

### 幻读

**幻读** 也发生在同一个事务内，但涉及范围查询。当事务A第一次执行一个范围查询（比如 `**age > 20**`）得到N条结果后，事务B **插入**了一条满足该条件的新记录或**删除**了一条原有记录并提交，事务A再次执行完全相同的范围查询时，结果集的行数变了（比如多了1条或少了一条）。它关注的是**结果集中行数的增减变化**，感觉像出现了‘幻影行’。

![img](https://cdn.nlark.com/yuque/0/2025/webp/53862437/1749799983272-da74a60f-c377-4b8c-9603-55966cd84521.webp)

## 事务隔离级别

SQL标准提出了四种隔离级别来规避这些现象，隔离级别越高，性能效率就越低，这四个隔离级别如下：

- 读未提交(read uncommitted)：指一个事务还没提交时，它做的变更就能被其他事务看到；
- 读提交(read committed)：指一个事务提交之后，它做的变更才能被其他事务看到；
- 可重复读(repeatableread)：指一个事务执行过程中看到的数据，一直跟这个事务启动时看到的数据是一致的，**MySQL InnoDB 引擎的默认隔离级别**；
- 串行化（serializable)：会对记录加上读写锁，在多个事务对这条记录进行读写操作时，如果发生了读写冲突的时候，后访问的事务必须等前一个事务执行完成，才能继续执行;

![img](https://cdn.nlark.com/yuque/0/2025/webp/53862437/1749800731636-7b47e754-aa6d-4973-b7f3-59ec0e113a25.webp)

## MVCC

多版本并发控制。通过数据行多个版本管理实现数据库的并发控制。

### Read View 

ReadView 就是事务在使用 MVCC 机制进行快照读操作时产生的读视图。当事务启动时，会产生数据库系统当前的一个快照，InnoDB 为每个事务构造了一个数组，用来记录并维护系统当前活跃事务的 ID。

Read View有四个重要的字段：

- m_ids：指的是在创建 ReadView 时，当前数据库中「活跃事务」的**事务id列表**，注意是一个列表，"**活跃事务**"指的就是，**启动了但还没提交的事务**。
- min_trx_id：指的是在创建 ReadView 时，当前数据库中「活跃事务」中事务**id最小的事务**，也就是m_ids的最小值。
- max_trx_id：这个并不是m_ids的最大值，而是创建ReadView时当前数据库中应该给下一个事务的id值，也就是**全局事务中最大的事务id值+1**;
- creator_trx_id：指的是**创建该Read View的事务的事务id**。

### 聚簇索引记录中两个跟事务有关的隐藏列

![img](https://cdn.nlark.com/yuque/0/2025/webp/53862437/1749801153471-97f88725-93a1-4bfe-bca0-0739100f316c.webp)

- trx_id，当一个事务对某条聚簇索引记录进行改动时，就会**把该事务的事务id记录在 trx_id 隐藏列里**;
- roll_pointer，每次对某条聚簇索引记录进行改动时，都会把旧版本的记录写入到undo日志中，然后这个**隐藏列是个指针，指向每一个旧版本记录**，于是就可以通过它找到修改前的记录

![img](https://cdn.nlark.com/yuque/0/2025/webp/53862437/1749801233606-a7442b04-eda0-42b0-9d20-823c77c4235f.webp)

一个事务去访问记录的时候，除了自己的更新记录总是可见之外，还有这几种

情况:

- 如果记录的 trx_id 值小于Read View中的 `min_trx_id` 值，表示这个版本的记录是在创建 ReadView 前已经提交的事务生成的，所以该版本的记录对当前事务可见。
- 如果记录的 trx_id 值大于等于ReadView中的 `max_trx_id` 值，表示这个版本的记录是在创建ReadView后才启动的事务生成的，所以该版本的记录对当前事务不可见。
- 如果记录的 trx_id 值在 Read View 的 min_trx_id 和 max_trx_id 之间，需要判断 trx_id 是否在 m_ids 列表中:

- 如果记录的 trx_id 在 m_ids 列表中，表示生成该版本记录的活跃事务依然活跃着（还没提交事务），所以该版本的记录对当前事务不可见。
-  如果记录的 trx_id不在 m_ids 列表中，表示生成该版本记录的活跃事务已经被提交，所以该版本的记录对当前事务可见。

## MySQL 可重复读隔离级别，完全解决幻读了吗？

## 快照读是如何避免幻读的？

MVCC 的 Read View

## 当前读是如何避免幻读的？

间隙锁

## 幻读被完全解决了吗？

没有，只是很大程度避免了幻读现象的发生。

 可重复读只能保证“同一类读”结果一致（快照读-快照读 / 当前读-当前读），无法保证“跨类型读”（快照读+当前读）的一致性。  

## 发生幻读现象的场景

| 时间点 | 事务 | 操作内容                                                     |
| ------ | ---- | ------------------------------------------------------------ |
| T1     | A    | **快照读** `SELECT * FROM t_test WHERE id > 100;` → 3条记录（快照读，产生 `ReadView`） |
| T2     | B    | 插入 `id = 200`，并 `COMMIT` 提交                            |
| T3     | A    | **当前读** `SELECT * FROM t_test WHERE id > 100 FOR UPDATE;` → 结果是 4条记录（包括 id=200） |









![img](https://cdn.nlark.com/yuque/0/2025/png/53862437/1748182002600-e8e30ad5-e20a-453c-abc2-6f9f1c409668.png)

#### 规则

有了这个ReadView，这样在访问某条记录时，只需要按照下边的步骤判断记录的某个版本是否可见。

- 如果被访问版本的trx_id属性值与ReadView中的 creator_trx_id 值相同，意味着当前事务在访问它自己修改过的记录，所以该版本可以被当前事务访问。 
- 如果被访问版本的trx_id属性值小于ReadView中的 up_limit_id 值，表明生成该版本的事务在当前事务生成ReadView前已经提交，所以该版本可以被当前事务访问。 
- 如果被访问版本的trx_id属性值大于或等于ReadView中的 low_limit_id 值，表明生成该版本的事务在当前事务生成ReadView后才开启，所以该版本不可以被当前事务访问。 
- 如果被访问版本的trx_id属性值在ReadView的 up_limit_id 和 low_limit_id 之间，那就需要判断一下trx_id属性值是不是在 trx_ids 列表中。

- 如果在，说明创建ReadView时生成该版本的事务还是活跃的，该版本不可以被访问。 
- 如果不在，说明创建ReadView时生成该版本的事务已经被提交，该版本可以被访问。

#### 整体操作流程

了解了这些概念之后，我们来看下当查询一条记录的时候，系统如何通过MVCC找到它：

1. 首先获取事务自己的版本号，也就是事务 ID； 
2. 获取 ReadView； 
3. 查询得到的数据，然后与 ReadView 中的事务版本号进行比较；
4. 如果不符合 ReadView 规则，就需要从 Undo Log 中获取历史快照； 
5. 最后返回符合规则的数据。

在隔离级别为读已提交（Read Committed）时，一个事务中的每一次 SELECT 查询都会重新获取一次 Read View。

如表所示：

![img](https://cdn.nlark.com/yuque/0/2025/png/53862437/1748182309035-a4dbe89d-da5f-499f-86ad-c032af0d2676.png)

注意，此时同样的查询语句都会重新获取一次 Read View，这时如果 Read View 不同，就可能产生不可重复读或者幻读的情况。

当隔离级别为可重复读的时候，就避免了不可重复读，这是因为一个事务只在第一次 SELECT 的时候会获取一次 Read View，而后面所有的 SELECT 都会复用这个 Read View，如下表所示：

# MySQL 字段类型 

## 面试题

### char 和 varchar 的区别是什么？

| 对比点         | `CHAR(n)`                          | `VARCHAR(n)`                       |
| -------------- | ---------------------------------- | ---------------------------------- |
| **长度固定？** | 是（定长）                         | 否（变长）                         |
| **存储空间**   | 固定 n 字节（不足补空格）          | 实际长度 + 1 或 2 字节的长度前缀   |
| **读取性能**   | 快（因为长度固定）                 | 相对慢（变长，要计算偏移）         |
| **适用场景**   | 长度固定的数据，如身份证号、状态码 | 长度可变的字段，如姓名、备注、地址 |

### varchar(100)和 varchar(10)的区别是什么？

| 对比项         | `VARCHAR(10)`      | `VARCHAR(100)`       |
| -------------- | ------------------ | -------------------- |
| 最大存储字符数 | 最多 10 个字符     | 最多 100 个字符      |
| 空间占用       | 小（变长但上限小） | 大（更可能产生碎片） |
| 行格式影响     | 紧凑               | 不紧凑，可能溢出页   |

MySQL 的一页大小为 **16KB**，如果一行数据太大，会触发“行溢出”，导致性能下降。

➡️ **结论：**
不要随便定义 varchar 很大，**尽可能****估算****业务****需要****的****最大****长度****再****定义**，否则会：

- 浪费内存
- 降低缓存命中率
- 增加行溢出风险

### decimal 和 float/double 的区别是什么？存储金钱应该用哪⼀种？

| 特性     | `DECIMAL(p, s)`                  | `FLOAT` / `DOUBLE`             |
| -------- | -------------------------------- | ------------------------------ |
| 精度     | **高精度**，定点数，适合财务运算 | 近似值，**有精度误差**         |
| 存储方式 | 字符串方式按位存储               | IEEE标准浮点数                 |
| 计算性能 | 较慢（需转换）                   | 快（硬件加速）                 |
| 典型用途 | **金钱、财务、库存数**           | 科学计算、图形计算、日志分析等 |

**金额存储必须使用** `**DECIMAL(p, s)**`**，绝不能用 FLOAT / DOUBLE**。这是数据库建模中最重要的规范之一。

### 为什么不推荐使用 text 和 blob？

| 特性     | `TEXT`（大文本）                  | `BLOB`（二进制大对象）   |
| -------- | --------------------------------- | ------------------------ |
| 用途     | 存储文章、描述等                  | 存图片、文件、音频等     |
| 存储方式 | 不存主表页内，而是放在 **溢出页** | 同上                     |
| 索引支持 | 仅支持前缀索引（不能全字段）      | 同上                     |
| 性能影响 | 读取慢、占用 IO、影响缓存命中     | 同上                     |
| 不支持   | 默认不能加 `DEFAULT` 值           | 不能直接参与部分函数操作 |

**使用****上****的****弊端**：

- 读取和更新成本高，不能像普通字段那样参与排序、全文检索。
- 缓存失效率高。
- 在分布式架构（如 MySQL 主从）中同步大字段可能造成延迟。

➡️ **替代****方案****建议**：

- 将大文本或二进制数据 **存储****在****专用****的****文件****系统****或****对象****存储**（如：MinIO、OSS），数据库中只存路径或URL。
- 若必须使用，考虑使用分表、冷热数据拆分等方案优化。





# MySQL 索引 

## 索引

索引是帮助 MySQL 高效获取数据的数据结构。

**本质：**索引为**数据结构**。在`存储引擎`中实现。

优点:

- **降低数据库的 IO 成本**
- 通过创建唯一索引，保证数据的唯一性
- 使用分组和排序子句进行数据查询时，可以显著减少查询中分组和排序的时间，降低了 CPU 的消耗。

缺点：

- 创建和维护索引耗费时间
- 索引占据磁盘空间
- 降低更新表的速度

## 数据页

记录按照行存储，但是 InnoDB 的数据时按 【数据页】为单位来读写的。

数据库 I/O 操作的最小单位是页，InnoDB 数据页的默认大小是 16kb。



![img](https://cdn.nlark.com/yuque/0/2025/webp/53862437/1749472414600-e7ad0b5b-a734-48fb-afbf-227de34d7fb0.webp)



![img](https://cdn.nlark.com/yuque/0/2025/webp/53862437/1749472448090-6e00567f-2cd1-446c-8508-c2148298c0d2.webp)

文件头有两个指针，连接起来的页相当于一个双向链表。

![img](https://cdn.nlark.com/yuque/0/2025/webp/53862437/1749472550328-56bd7cc7-cea1-4d37-a5c7-020f1ebe491f.webp)

数据页中记录按照【主键】顺序组成单向链表，页目录的存在能够找到记录。

页目录创建过程：

- 将所有的记录划分成几个组，这些记录包括最小记录和最大记录，但不包括标记为”已删除”的记录；

第一个分组中的记录只能有1条记录；

最后一个分组中的记录条数范围只能在1-8条之间；

剩下的分组中记录条数范围只能在4-8条之间。

- 每个记录组的最后一条记录就是组内最大的那条记录，并且最后一条记录的头信息中会存储该组一共有多少条记录，作为n_owned字段（上图中粉红色字段）
- 页目录用来存储每组最后一条记录的地址偏移量，这些地址偏移量会按照先后顺序存储起来，每组的地址偏移量也被称之为槽（slot），每个槽相当于指针指向了不同组的最后一个记录。

![img](https://cdn.nlark.com/yuque/0/2025/webp/53862437/1749472601336-10732d51-4155-4c5e-aaed-4055356e6345.webp)



## 聚簇索引、二级索引

**区别：**

- 聚簇索引的叶子节点存放的是实际数据，所有完整的用户记录都存放在聚簇索引的叶子节点;
- 二级索引的叶子节点存放的是主键值，而不是实际数据。

![img](https://cdn.nlark.com/yuque/0/2025/webp/53862437/1749475971652-4e3aa4ce-7bc3-4975-82ce-6cc464e58d22.webp)

| 数据页类型                 | 页内容                           | 是否有行数据               |
| -------------------------- | -------------------------------- | -------------------------- |
| **非叶子节点页**           | `key + 子页指针（PageNo）`       | ❌ 没有行数据               |
| **叶子节点页（聚簇索引）** | `key + 行记录数据（完整的一行）` | ✅ 有（行数据）             |
| **叶子节点页（二级索引）** | `key + 主键值（作为回表依据）`   | ❌ 没有行数据，但能回表定位 |



### 回表、索引覆盖

查询语句使用了二级索引，但是查询数据不是主键值，这时需要去聚簇索引中获得数据行，这个过程就叫【回表】，需要查询**两**个 B+ 树。

当查询数据为主键值时，在二级索引就能查询到，这个过程叫做【索引覆盖】。

## 索引的类型

- 按「数据结构」分类：B+tree索引、Hash索引、Full-text索引。
- 按「物理存储」分类：聚簇索引（主键索引)、二级索引（辅助索引)。
- 按「字段特性」分类：主键索引、唯一索引、普通索引、前缀索引。
- 按「字段个数」分类：单列索引、联合索引。

- 但 Hash 表不适合做范围查询。

## 行级锁

不同隔离级别下，行级锁的种类是不同的。

在读已提交隔离级别下，行级锁的种类只有记录锁，也就是仅仅把一条记录锁上。

在可重复读隔离级别下，行级锁的种类除了有记录锁，还有间隙锁（目的是为了避免幻读），所以行级锁的种类主要有三类：

- Record Lock，记录锁，也就是仅仅把一条记录锁上;
- Gap Lock，间隙锁，锁定一个范围，但是不包含记录本身；
- Next-Key Lock:Record Lock +Gap Lock的组合，锁定一个范围，并且锁定记录本身。

### Record Lock

记录锁，锁住一条记录。有 S 锁和 X 锁之分（不兼容）：

S 与 S 共存其他都不可以。

当事务执行 commit 后，事务过程生成的锁都会被释放。

### Gap Lock

GapLock称为间隙锁，存在于可重复读隔离级别和串行化隔离级别，目的是为了解决可重复读隔离级别下幻读的现象。



### Next-Key Lock

为 Record Lock + Gap Lock 组合，锁住范围和记录本身。

next-key lock是包含间隙锁+记录锁的，如果一个事务获取了X型的 next-key-lock，那么另外一个事务在获取相同范围的x型的next-keylock时，是会被阻塞的。

# MySQL 日志 

- redolog：实现事务持久性，
- undolog：实现事务原子性，用于事务回滚和MVCC
- binlog：二进制日志，用于数据备份和主从备份

## UndoLog日志原理

1. **为了事务回滚（原子性）**：undo log 记录通过**事务内部的指针 (\****undo_next_log)** 组织成一个**每个事务私有**的链表。回滚时遍历这条私有链。
2. **为了 MVCC（隔离性）**：undo log 记录通过**数据行上的****DB_ROLL_PTR（事务指针）** 和 **undo log****记录之间的指针**，组织成一个**针对特定数据行的公共历史版本链**。快照读时遍历这条公共链。

## RedoLog

BufferPool 提高了数据交互的速度，WAL技术，保证了 redolog 安全落地，且redolog写入方式为追加，顺序写比磁盘的随机写，效率更高。（redolog为**物理日志**）通过LSN技术，实现故障恢复。（事务提交但脏页未刷盘）

BufferPool作为数据库与磁盘的“内存”。以数据页形式存在，一页大小为16kb。

## BinLog日志原理

server层日志，追加写，用于数据恢复与主从备份。

三种格式类型：语句格式，行格式，混合格式

事务提交有redolog和binlog需要写，需要保证原子性，不然会出现主从不一致情况。引入二阶段提交。

1. Prepare

redolog 写入

1. Commit

binlog 写入

崩溃恢复

通过在binlog寻找事务ID。

有则，commit，成功。没有，则回滚。

## 只用BinLog不用RedoLog

1. Buffer Pool 中的每个**脏页**，都会记录下导致其变更的**最后一次****redo log****的 LSN**（即 page_lsn）。
2. **Checkpoint** 机制会定期将某个 LSN（checkpoint_lsn）之前的所有脏页刷回磁盘，并记录这个 checkpoint_lsn 作为安全恢复点。
3. 当数据库**崩溃重启**时，它只需要找到最后一次成功的 checkpoint_lsn，然后**重放 (Redo)** 从该 checkpoint_lsn 到 redo log 文件末尾的所有日志记录，即可将数据库恢复到崩溃前的最终一致性状态。

LSN为一个**全局的、单调递增**的计数器

## 为什么需要 undo log？

1. **核心目的定位：解决事务的“回滚”需求 (原子性保证)**

- **核心需求：** 事务要么全部成功（Commit），要么全部失败回滚（Rollback）。这是事务 ACID 特性中**原子性（Atomicity）** 的基本要求。
- **问题：** 如果一个事务在执行过程中修改了数据（INSERT/UPDATE/DELETE），但在提交前失败了（系统崩溃、显式ROLLBACK、死锁被选为牺牲者等），数据库必须有能力**将数据恢复到该事务开始前的状态**。
- **解决方案：Undo Log！** Undo Log 的核心作用就是**记录数据修改前的旧值（或旧版本）**。当事务需要回滚时，数据库引擎可以利用 Undo Log 中的信息，**逆向执行逻辑操作**（比如，将 UPDATE 的新值改回旧值，将 INSERT 的新行删除，将 DELETE 的行重新插入），从而撤销该事务的所有影响，保证原子性。**没有 Undo Log，可靠的回滚机制就无法实现。**

1. **支撑 MVCC 与一致性非锁定读 (并发控制与隔离性)**

- **核心需求：** 在高并发场景下，需要让不同的事务看到数据库在**不同时间点的一致性视图**，特别是 `**REPEATABLE READ**` 和 `**READ COMMITTED**` 隔离级别。同时，避免读操作长时间阻塞写操作（非锁定读）。
- **解决方案：MVCC (多版本并发控制)**
- **Undo Log 的作用：** Undo Log 不仅仅是记录旧值用于回滚。它实际上**保存了数据行的历史版本**。

- 当一个事务启动时，它会获得一个唯一的、单调递增的事务ID (`**trx_id**`)。
- 当进行写操作（UPDATE/DELETE）时，InnoDB 不会立即覆盖原数据页上的行，而是：

- 将当前行的旧版本数据（修改前的值）写入 Undo Log。
- 在当前数据页上创建该行的**新版本**，并标记这个新版本是由哪个事务ID (`**trx_id**`) 创建的。
- 新版本的行中包含一个指针（`**roll_pointer**`），指向上一个版本在 Undo Log 中的位置，形成一个**版本链**。

- 当一个读操作（普通 `**SELECT**`，非 `**FOR UPDATE/LOCK IN SHARE MODE**`）发生时：

- 读操作会带上它启动时的事务ID (`**trx_id**`) 或系统当前的“一致性读视图”。
- 它沿着数据页上最新版本的行开始，根据 `**roll_pointer**` 遍历 Undo Log 中的版本链。
- 找到第一个**创建该版本的事务ID** `**trx_id**` **<= 读操作的事务ID/视图ID** 且**该版本的事务已经提交**的版本（或者是最早的未修改版本），将这个版本的数据返回给读操作。

- **为什么需要：** Undo Log 保存的历史版本，使得：

- **读操作不需要加锁** 就能看到一致的快照数据（非锁定读），极大提高了并发读性能。
- 实现了 `**REPEATABLE READ**` 隔离级别：一个事务内的多次普通读，看到的是它启动时的快照（通过访问 Undo Log 中的历史版本来实现），避免了不可重复读（对于快照读）。
- 实现了 `**READ COMMITTED**` 隔离级别：每次读都看到最新已提交的快照（也是通过访问 Undo Log 中合适的版本来实现）。

1. **辅助崩溃恢复 (Crash Recovery)**

- **场景：** 数据库服务器意外崩溃重启。
- **问题：** 崩溃时可能有不完整的事务（既未提交也未明确回滚）修改了数据页。
- **解决方案结合：** InnoDB 的崩溃恢复主要依赖 **Redo Log** 来重做已提交但未刷盘的操作（保证持久性）。但 Redo Log 只记录了“重做”操作（物理逻辑日志）。
- **Undo Log 的作用：** 在崩溃恢复阶段，数据库需要处理那些在崩溃时处于 `**ACTIVE**` 状态（未提交）的事务。Redo Log 重做后，这些未提交事务的修改也会被重做到数据页上。此时，数据库需要利用 **Undo Log 来回滚这些未提交的事务**，将它们对数据页的修改撤销掉，保证只有已提交事务的修改最终生效。**没有 Undo Log，就无法在崩溃后正确回滚未完成的事务，破坏原子性。**





## undo log 如何执行？

**Undo Log 操作的标准流程和原理：**

1. **触发时机 (核心)：**

- **当且仅当事务执行** `**INSERT**`**,** `**UPDATE**`**,** `**DELETE**` **这类会修改数据的 DML 语句时，才会生成 Undo Log。**
- **在修改实际数据页（Buffer Pool 中的页）之前，必须先将修改前的数据（旧版本）写入 Undo Log。**
- **事务开始时 (**`**BEGIN**` **/** `**START TRANSACTION**`**)** 本身**不会**产生 Undo Log。Undo Log 的生成是**伴随数据修改操作**发生的。

1. **写入内容：**

- **不是 SQL 语句！** Undo Log 记录的是**修改前的数据值**或**必要信息**：

- `**UPDATE**`**：** 记录被修改字段的**旧值** (Old Values)。回滚时，用这些旧值覆盖新值。
- `**DELETE**`**：** 记录被删除行的**所有列的值** (相当于整行数据的拷贝)。回滚时，将这些值重新插入原表。
- `**INSERT**`**：** 记录新插入行的**主键值** (或唯一标识信息)。回滚时，根据这个主键值删除该行。

- 它是一种**逻辑日志**，记录了如何撤销修改所需的最少信息。

1. **写入过程 (Write-Ahead Logging Principle - WAL 的延伸)：**

1. 事务发起一个修改操作（如 `**UPDATE t SET col = 'new' WHERE id = 1**`）。
2. **步骤 1 (Undo Logging)：**

- InnoDB 定位到要修改的数据行（`**id=1**`）。
- **在修改内存中的 Buffer Pool 数据页之前，将** `**col**` **字段的旧值（比如** `**'old'**`**）写入 Undo Log Buffer (内存缓冲区)。**
- 同时，为了保证 Undo Log 本身的持久性，这个 Undo Log 记录的写入操作**也会被记录到 Redo Log Buffer** (因为修改 Undo Log 也是一种数据修改，需要 Redo 保护)！这是关键点。

1. **步骤 2 (Redo Logging)：** 将 `**UPDATE**` 操作本身的 Redo Log 记录写入 Redo Log Buffer (记录如何重做这个修改)。
2. **步骤 3 (Write & Flush)：**

- 在合适的时机（如事务提交时、Log Buffer 满时、后台线程刷盘时），Redo Log Buffer 的内容会被**顺序、批量**地写入磁盘的 Redo Log File。**这个刷盘动作保证了即使崩溃，已提交事务的修改和相关的 Undo Log 都不会丢失。**
- Undo Log Buffer 的内容也会被写入磁盘的 Undo Tablespaces (专门的 Undo 表空间文件)，但这个刷盘通常不像 Redo Log 那样要求必须在事务提交前强制刷（因为 Undo 主要用于回滚和 MVCC，其持久性由 Redo Log 间接保证）。

1. **步骤 4 (Modify Data Page)：** 最后（或在过程中），修改内存 Buffer Pool 中的数据页，将 `**col**` 的值更新为 `**'new'**`。这个脏页会在后续由 Checkpoint 机制刷回磁盘数据文件。

1. **回滚操作 (Rollback)：**

- 当需要回滚事务（`**ROLLBACK**` 或崩溃恢复时回滚未提交事务）时：
- **不是 "逆执行 SQL 语句"！**
- 数据库引擎（InnoDB）会根据该事务产生的 **Undo Log Records**：

- 对于 `**UPDATE**`：找到对应的 Undo Log，取出旧值 `**'old'**`，将 `**id=1**` 的行的 `**col**` 字段**覆盖**回 `**'old'**`。
- 对于 `**DELETE**`：取出 Undo Log 中记录的整行数据值，**重新插入**到原表中。
- 对于 `**INSERT**`：取出 Undo Log 中记录的主键值，**删除**该主键对应的行。

- 这个过程是**物理层面的数据恢复**，而不是执行 `**UPDATE t SET col = 'old'...**` 这样的反向 SQL。

1. **MVCC 读操作 (非锁定读)：**

- 当一个读事务需要访问某个数据行的历史版本时（比如在 `**REPEATABLE READ**` 隔离级别下，该行在它启动后被其他事务修改过）：
- 数据行本身（在 Buffer Pool 或磁盘上）通常存储的是**最新版本**。
- 该行记录中包含一个 `**roll_pointer**` 字段，指向该行的**上一个版本在 Undo Log 中的位置**。
- 读事务沿着这个 `**roll_pointer**` 形成的**版本链**，在 **Undo Log 中查找**符合其可见性规则（由其事务ID `**trx_id**` 和 Read View 决定）的旧版本数据。

**总结与面试回答要点：**

- **Undo Log 的写入时机：** **在修改数据页之前**，伴随 `**INSERT**`/`**UPDATE**`/`**DELETE**` 操作发生，**不是**事务开始时或执行语句前。
- **Undo Log 的内容：** 记录修改前的**数据旧值/状态**（`**UPDATE**` 的旧值、`**DELETE**` 的整行数据、`**INSERT**` 的主键），**不是逆操作的 SQL 语句**。
- **Undo Log 的持久化：** 写入 Undo Log Buffer，并最终写入 Undo Tablespace。其**持久性由 Redo Log 间接保证**（因为写 Undo Log 本身这个动作也会产生 Redo Log）。
- **回滚机制：** 利用 Undo Log 中的旧数据，**直接覆盖或插入/删除数据行**，进行物理层面的恢复。
- **MVCC 机制：** 通过 `**roll_pointer**` 形成版本链，**读操作访问 Undo Log 中的历史版本**来实现一致性非锁定读。
- **核心目的：**

- **原子性 (Atomicity)：** 提供精确的回滚能力。
- **隔离性 (Isolation)：** 支撑 MVCC，实现一致性读视图。
- **崩溃恢复：** 回滚未完成事务的修改。

**优秀面试回答示例：**

“Undo Log 是 InnoDB 实现事务原子性和 MVCC 的关键机制。它的操作流程是这样的：

1. **写入触发：** 当事务执行 `**INSERT**`, `**UPDATE**`, `**DELETE**` 等**数据修改操作时**，**在真正修改内存数据页之前**，系统会先将**修改前的数据状态**写入 Undo Log：

- 对 `**UPDATE**`，记录被修改字段的**旧值**。
- 对 `**DELETE**`，记录被删除行的**完整数据**。
- 对 `**INSERT**`，记录新插入行的**主键标识**。

1. **持久化保证：** 写入 Undo Log 的操作本身也会被记录到 **Redo Log**，确保即使崩溃，Undo Log 信息也不会丢失（遵循日志先行原则）。
2. **回滚操作：** 当事务回滚时，**不是逆执行 SQL**，而是**根据 Undo Log 中记录的旧数据**：

- 用 `**UPDATE**` 记录的旧值**覆盖**新值。
- 将 `**DELETE**` 记录的完整数据**重新插入**回表。
- 根据 `**INSERT**` 记录的主键**删除**新插入的行。

1. **MVCC 读：** 对于一致性读（如 `**REPEATABLE READ**` 下的普通 `**SELECT**`），当需要访问旧版本数据时，会通过数据行上的 `**roll_pointer**` **在 Undo Log 的版本链中查找**符合事务 Read View 的历史版本。

因此，Undo Log 的核心在于**在数据修改前保存旧状态**，为事务的**原子性回滚**和 **MVCC 多版本读**提供了基础支持。它的写入是与数据修改操作紧密绑定的，记录的是数据本身的变化历史，而非反向 SQL 语句。”



## 为什么需要 Buffer Pool？

1. **核心矛盾：磁盘I/O vs 内存速度的鸿沟**

- 磁盘（尤其是机械硬盘）的随机读写速度比内存慢 **10万倍以上**（内存纳秒级 vs 磁盘毫秒级）。
- 若每次数据库操作都直接读写磁盘，系统会因I/O等待彻底卡死。

1. **解决方案：用空间换时间**

- Buffer Pool 的本质是 **内存缓存区**，通过将高频访问的磁盘数据暂存到内存，将随机磁盘I/O转化为内存操作，**性能提升数个数量级**。

1. **对数据库的深层价值：**

- **降低延迟**：内存访问速度是磁盘的 105∼106105∼106 倍。
- **减少磁盘压力**：合并多次写操作（如脏页刷盘），避免频繁小数据量I/O。
- **保护事务持久性**：配合 Redo Log，实现 **WAL（Write-Ahead Logging）** 机制（先写日志再改内存，崩溃后通过日志恢复）。

## Buffer Pool 缓存什么？



![img](https://cdn.nlark.com/yuque/0/2025/png/53862437/1751507909643-de740572-e0e1-4bba-ada0-27560067e6ef.png)

1. **核心缓存：数据页与索引页（占比 >99%）**

- **数据页 (Data Pages)**：表的行数据（`***.ibd**`文件中的用户数据）。
- **索引页 (Index Pages)**：

- B+树非叶子节点（定位路径）
- B+树叶子节点（存储实际数据或主键+二级索引）

✅ **关键认知**：索引即数据，InnoDB 中二级索引叶子节点存储 **主键值**，回表查询依赖主键索引。

1.  **辅助结构：优化特定场景**

- **Change Buffer（写缓冲）**：

- **缓存场景**：对**非唯一二级索引**的 `**INSERT/UPDATE/DELETE**` 操作
- **作用**：延迟写入磁盘，减少随机I/O（后续读取时合并写入）。
- 📊 **典型效果**：写入密集型场景性能提升 10 倍以上（如日志表）。

- **Adaptive Hash Index（自适应哈希索引）**：

- **缓存场景**：自动为**高频访问的索引页**构建哈希索引。
- **作用**：将 B+树 O(logN)*O*(*l**o**g**N*) 查询优化为 O(1)*O*(1)。

- **Lock System Memory**：

- 缓存行锁信息（避免每次锁操作访问磁盘）。

**冷知识：Page 是管理的最小单位**

- 每页默认 **16KB**，包含页头（Page Header）、行记录（Row Records）、页尾（Page Trailer）等元数据。
- Buffer Pool 以 **Page 为单位** 加载/淘汰数据。

“Buffer Pool 本质是 **磁盘数据的‘镜像’**，但通过内存加速 + 智能管理（LRU算法、预读机制），让随机I/O表现为顺序访问。”

### 慢查询日志有什么用？


### binlog 主要记录了什么？

binlog 是 MySQL 层（Server 层）日志，**记录****所有****更改****数据****的****语****句**，如：

- `INSERT`, `UPDATE`, `DELETE`
- 不记录 `SELECT`、`SHOW`等查询语句

📝 记录格式有三种：

| 格式      | 说明                           |
| --------- | ------------------------------ |
| STATEMENT | 记录原始 SQL 语句（体积小）    |
| ROW       | 记录每一行数据的变更（更精确） |
| MIXED     | 混合模式，根据情况自动选用     |

**作用**：

- 事务恢复（结合 redo log）
- 主从复制（从库重放 binlog）
- Point-in-Time 恢复（PITR）

### redo log 如何保证事务的持久性？

### 🔁 事务提交流程简化如下：

1. 写 redo log（先写入 WAL buffer）
2. 写 binlog
3. redo log 标记为 commit 状态
4. **才****返回****客户****端“****事务****提交****成功”**

这个机制叫 **WAL（****Write-****Ahead** **Logging）****预****写****日志****机制**：

数据页修改**先****写****日志，****再****异步****刷****盘**

📌 **特点**：

- 崩溃恢复时，只要 redo log 中有 commit 日志，就能恢复数据
- 支持 crash-safe（即使服务器宕机也不会丢数据）



### 页修改之后为什么不直接刷盘呢？

因为磁盘 IO 非常慢，频繁刷盘将严重拖慢事务执行速度。

更好的策略是：

- 先修改 **内存****中的** **Buffer** **Pool** **页**
- 把修改写入 **redo** **log（****WAL****机制）**
- 等系统空闲或数据页脏页超过阈值，再批量刷盘

这叫做 **延迟****刷****盘 +** **WAL****日志****先行**：

- 提高性能
- 保证一致性和可靠性

### binlog 和 redolog 有什么区别？

| 比较维度   | binlog              | redo log               |
| ---------- | ------------------- | ---------------------- |
| 属于哪一层 | Server 层           | InnoDB 引擎层          |
| 写入时机   | 提交事务时          | 修改数据时             |
| 作用       | 主从复制、增量备份  | Crash 恢复，保证持久性 |
| 是否可覆盖 | 追加写，不覆盖      | 循环写                 |
| 格式       | Statement/Row/Mixed | 固定格式（二进制）     |
| 持久性保证 | 无法独立恢复        | 是 crash-safe 的关键   |

### undo log 如何保证事务的原子性？

undo log 是事务**回滚操作的基础**，记录了“修改前”的旧值。



```sql
BEGIN;
UPDATE user SET balance = balance - 100 WHERE id = 1;
-- 此时会记录一条 undo log：balance 的旧值

ROLLBACK;
-- 事务失败，根据 undo log 恢复旧值，实现回滚
```

📌 特点：

- 保证原子性：失败时能完整回滚
- 支持 MVCC：提供快照读的“旧版本视图”
- 存储在：InnoDB 的 `undo tablespace`

### 数据冷热分离如何做？

✅ 定义：

- 热数据：最近活跃数据，查询频繁
- 冷数据：历史归档数据，查询少

✅ 实现方式：

1. **按****时间****分****表**（如订单表按月拆）
2. **冷****热****表****拆****分**（热表只有近1个月，冷表为归档）
3. **存储****介质****冷****热****分离**：

- 热数据存 SSD
- 冷数据存 SATA 或离线存储（HDFS）

1. **通过程序或中间件路由访问热/冷表**

### 常见的数据库优化方法有哪些？

| 优化维度 | 方法                                       |
| -------- | ------------------------------------------ |
| SQL 优化 | 索引、覆盖索引、避免全表扫描、SQL 重写     |
| 结构优化 | 垂直拆分、水平拆分、冷热分离               |
| 索引优化 | 聚簇索引、最左匹配、避免过多索引           |
| 存储引擎 | 合理选择 InnoDB/MyISAM 等                  |
| 并发优化 | 使用合适隔离级别、减少锁冲突               |
| 系统层面 | 提升内存、磁盘性能、参数调优               |
| 缓存层   | Redis / CDN 缓存热点数据                   |
| 架构层面 | 主从同步、读写分离、分库分表、数据库中间件 |

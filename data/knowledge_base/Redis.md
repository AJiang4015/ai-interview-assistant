## 分布式锁

一个靠谱的分布式锁需具备的条件与刚需

- 独占性

任何时刻有且只能有一个线程持有

- 高可用

若为redis集群环境下，不能因为某一个节点挂了而出现获取锁和释放锁失败的情况高并发请求下，依旧性能OK好使

- 防死锁

杜绝死锁，必须有超时控制机制或者撤销操作，有个兜底终止跳出方案

- 不乱抢

防止张冠李戴，不能私底下unlock别人的锁，只能自己加锁自己释放

- 重入性

同一个节点的同一个线程如果获得锁之后，它也可以再次获取这个锁

### SetNX

过期时间难以设置。

无法判断当前锁的持有者。

解锁不是原子的。

不支持锁续期。

重入锁需要 hset 实现。

引入 lua 脚本实现原子解锁。

### Redisson

由于 Redis 复制为异步，SetNX 无法保证在主机故障时，不会出现一锁被多建问题。

使用 RedLock 算法用于实现多个实例的分布式锁问题，已改为 MultiLock 算法。

#### RedLock

- 同时向 N 个 Redis 节点发起加锁请求。
- 如果半数以上（一般为 N/2+1）节点加锁成功且耗时不超过锁超时时间的一半，则认为加锁成功。
- 解锁时向所有加锁成功的实例释放锁。

#### MultiLock

- 所有指定锁全部加锁成功才算成功
- 任一失败立即回滚
- 所有锁全部释放

#### 加锁、可重入、续命、解锁

Redisson 使用 **Hash + ThreadId 作为锁标识，实现可重入**

**续命的 watch dog自动延期机制：**

源码中初始化了一个定时器，dely的时间是 internalLockLeaseTime / 3。

在Redisson中，internalLockLeaseTime 是获取配置的看门狗的时间，默认是30s，也就是每隔10s续期一次，每次重新设置过期时间为30s。

### 如何实现跳表？

```plain
class SkipListNode {
    Object value;
    double score;
    SkipListNode backward; // 指向前一个节点，用于从后往前遍历
    Level[] level; // 指针数组

    class Level {
        SkipListNode forward; // 指向同一层的下一个节点
        int span; // 跨度，表示这个指针跳过了多少个节点
    }
}

// p 是一个概率因子，通常是 0.5 (像抛硬币) 或 0.25
private static final double P_FACTOR = 0.5;
private static final int MAX_LEVEL = 32; // 跳表的最大层高

private int randomLevel() {
    int level = 1; // 新节点的层高至少是 1 (对应 Level 0)
    // 循环抛硬币
    while (Math.random() < P_FACTOR && level < MAX_LEVEL) {
        level++;
    }
    return level;
}
```

### 为什么不直接用 C 的 `char*`？

C 字符串的问题：

- 不能记录长度，只能遍历到 `\0`
- 修改时容易造成缓冲区溢出
- 扩容不方便

| **优点**       | **说明**                      |
| -------------- | ----------------------------- |
| 记录长度       | `O(1)` 获取长度，避免多次遍历 |
| 自动扩容       | append 自动增长空间           |
| 二进制安全     | 可存任意字节，不依赖 `\0`     |
| 减少内存重分配 | 使用“空间冗余”策略提高性能    |

### Redis 为什么用跳表，而不用平衡树、红黑树或者B+树？

跳表（Skip List）是 ZSet 的底层结构之一（配合 Hash）

| **特性**       | **跳表（SkipList）** | **红黑树**      | **B+树**                |
| -------------- | -------------------- | --------------- | ----------------------- |
| 插入删除复杂度 | O(logN)（简单）      | O(logN)（复杂） | 较复杂                  |
| 编码复杂度     | 简单易实现           | 实现复杂        | 适合磁盘存储            |
| 范围查询       | 快速支持             | 支持            | 强（磁盘环境优）        |
| 有序性         | 支持                 | 支持            | 支持                    |
| 内存存储       | 更适合               | 可以            | 不合适（B+ 更适合磁盘） |

Redis 是 **内存数据库**：

- 不追求极限树结构效率；
- 跳表在内存中速度稳定、实现简单；
- 支持范围查询、rank 查询、分页等高级功能。

### Redis为什么使用 ListPack 替代 ZipList?

istPack 是 ZipList 的升级优化版本，Redis 5.0 开始引入，7.0 默认替代 ZipList。

| **ZipList 缺陷**   | **ListPack 优化**            |
| ------------------ | ---------------------------- |
| 插入/删除代价高    | 用 offset 替代指针，提高效率 |
| 内存碎片大         | 更紧凑编码，减少空间浪费     |
| 访问效率差         | 简化结构，加快查找           |
| 单个元素编码不统一 | 定长变长兼容，压缩效果更好   |

ListPack 应用：

- 小型 Hash、ZSet、List 的底层结构；
- Redis 会自动判断结构大小并在 ZipList 与 Dict/SkipList/QuickList 之间切换。

#### 步骤 1：客户端发送写命令

Redis 是单线程模型，多个客户端通过 epoll 多路复用进入 Server，依次执行命令。

#### 步骤 2：命令追加到 AOF 缓冲区（`server.aof_buf`）

Redis 在内存中有一块叫 `aof_buf`的缓冲区，这是 AOF 缓冲区的本质。

- 它不是系统内核缓冲，而是 Redis 的用户态内存（user space）
- 所有**修改\****类命令**（如 `SET`、`INCR`、`HSET`等）执行后都会被转成 Redis 协议格式，追加进 `aof_buf`

**目的**：减少频繁磁盘 IO，支持批量写入

#### 步骤 3：调用 `write()`将 `aof_buf`写入内核缓冲区（page cache）

Redis 会定期将 `aof_buf`的内容使用系统调用 `write()`写入 OS 的 `page cache`（也叫 OS 缓冲区）

此时数据还没真正写入磁盘，而是写入了 Linux 内核管理的磁盘缓冲页中。

#### 步骤 4：刷盘（flush）策略

数据何时真正写入磁盘（即从 page cache → 磁盘）取决于你设置的 AOF 写策略

#### 步骤 5：AOF 重写（AOF Rewrite）

随着 AOF 文件不断追加，会越来越大。Redis 会通过 **后台子进程（fork）进行 AOF 重写**，优化日志内容。

### 三种写回策略

| **写策略**       | **写回时机**                                 | **优点**                         | **缺点**                           |
| ---------------- | -------------------------------------------- | -------------------------------- | ---------------------------------- |
| always           | 每次写入命令都执行一次 `fsync()`，最安全最慢 | 可靠性高，最大程度保证数据不丢失 | 每个写命令都要写回硬盘，性能开销大 |
| everysec（默认） | 每秒执行一次 `fsync()`，推荐策略             | 性能适中                         | 宕机时丢失 1s 内的数据             |
| no               | 由操作系统决定刷盘时机，最快但风险最高       | 性能好                           | 宕机时丢失的数据可能会很多         |

通过控制 fsync() 函数调用时机

### 重写机制

当 AOF 文件大小超过阈值，Redis 启用 AOF 重写机制。

- 重写不是压缩原文件，而是**重\****构一份新的** **AOF****文件**
- 它会扫描内存中当前数据，然后生成一组最简命令写入新文件
- 重写后 Redis 会将新旧文件合并并替换

| **步骤** | **说明**                                                     |
| -------- | ------------------------------------------------------------ |
| 1️⃣        | Redis 主线程 `fork()`一个子进程（后台运行）                  |
| 2️⃣        | 子进程读取内存数据（当前所有 key-value）并生成 **最小命令集合**，写入一个**新临时 AOF 文件**（如 `temp-rewrite.aof`） |
| 3️⃣        | 与此同时主线程继续接收客户端命令，这些新命令仍然写入 **aof_buf 缓冲区 和 旧 AOF 文件**（继续保障旧文件可恢复） |
| 4️⃣        | 子进程构建完成后，主线程会将 **缓冲区中的差异命令** 也追加到新临时 AOF 文件末尾 |
| 5️⃣        | Redis 使用 `rename()`原子替换旧 AOF 文件，完成重写替换       |

| **阶段**                 | **执行者**               | **说明**                                                     |
| ------------------------ | ------------------------ | ------------------------------------------------------------ |
| `write()`调用            | Redis 子进程             | 把构造的命令写入临时 AOF 文件（这时是写入 OS 的页缓存 Page Cache） |
| `fsync()`/ `fdatasync()` | Redis 主进程（依据配置） | 把 Page Cache 中的数据刷入磁盘，确保真正持久化               |
| 实际磁盘写入             | 操作系统内核             | 执行真正的磁盘 I/O                                           |

| **是否看到 AOF 文件** | **是否代表刷盘完成** | **是否能恢复数据** |
| --------------------- | -------------------- | ------------------ |
| `write()` 后看到      | ❌ 不代表刷盘完成     | ❌ 有丢失风险       |
| `fsync()` 后完成      | ✅ 真正落盘           | ✅ 数据安全         |

直接复用现有 AOF 文件可能造成污染。

### 后台重写

由后台子进程 bgrewriteaof 完成。

好处：

- 避免阻塞主进程
- 子进程带有主进程的数据副本，线程之间共享内存，需加锁保证线程安全，降低性能。父子进程共享内存数据，当内存数据发生修改时，发生**写时复制**。

##### 写时复制

写时复制（COW）机制流程如下：

1. **fork****创建\****子进程**：

- 父进程与子进程拥有**独立\****的页表（Page** **Table）**；
- **页\****表项映射的物理内存页相同**（共享物理内存）；
- **页\****表项的权限都被设置为只读**（Read-Only）；
- 这样，如果谁尝试写，就会触发页保护异常。

1. **当主\****进程（或子进程）尝试修改一页内存时**：

- CPU 检查页表，发现该页是只读，触发**写\****保护中断（Page** **Fault）**；
- 操作系统会进行 **拷贝\****该页内容到新物理页（仅该页，不是全部内存）**；
- 父进程（写的那个）更新页表项，**映射\****到新物理页**，并将该页表项设为可读写；
- 子进程页表**仍\****指向旧物理页**，**仍然是只读**，不受影响；
- 所以父子两进程在写时就“分道扬镳”，从共享变为私有。

为了解决父子进程间数据不一致问题，Redis 设置了 AOF 重写缓冲区，在创建子进程后开始使用。

在 bgrewriteaof 子进程执行AOF重写期间，主进程需要执行以下三个工作：

- 执行客户端发来的命令;
- 将执行后的写命令追加到「AOF缓冲区」;
- 将执行后的写命令追加到「AOF重写缓冲区」;

当子进程完成AOF重写工作（扫描数据库中所有数据，逐一把内存数据的键值对转换成一条命令，再将命令记录到重写日志）后，会向主进程发送一条信号，信号是进程间通讯的一种方式，且是异步的。

主进程收到该信号后，会调用一个信号处理函数，该函数主要做以下工作：

将AOF重写缓冲区中的所有内容追加到新的AOF的文件中，使得新旧两个AOF文件所保存的数据库状态一致；

新的AOF的文件进行改名，覆盖现有的AOF文件。

信号函数执行完后，主进程就可以继续像往常一样处理命令了。

##### 页表

页表是操作系统为每个进程维护的虚拟内存 → 物理内存的映射表。

| **概念**                            | **描述**                                                     |
| ----------------------------------- | ------------------------------------------------------------ |
| **虚拟内存（Virtual Memory）**      | 进程看到的“假象地址空间”，每个进程都有自己独立的虚拟地址空间（如 0x0000 ~ 0xFFFF）。 |
| **物理内存（Physical Memory）**     | 实际的 RAM 内存地址。                                        |
| **页表（Page Table）**              | 将虚拟地址空间分成一页页（通常 4KB），由页表记录每一页的虚拟地址对应的物理地址。 |
| **页表项（Page Table Entry, PTE）** | 页表中的每一项，记录：虚拟页 → 物理页的映射关系、读写权限、是否在磁盘、是否共享等。 |

为什么虚拟内存不同？

因为**每个进程都有自己独立的地址空间**，虽然可能映射到相同的物理内存，但它们的页表是独立的，所以虚拟地址空间是隔离的。

### RDB 快照会阻塞主线程吗？

Redis 提供了两个命令来生成 RDB 快照文件：

- `save` : 同步保存操作，会阻塞 Redis 主线程；

### 宕机了，Redis 如何避免数据丢失？

| **机制**               | **描述**                                          | **优势**                     | **风险**                                   |
| ---------------------- | ------------------------------------------------- | ---------------------------- | ------------------------------------------ |
| **RDB（快照）**        | 定期将内存快照保存为二进制文件（`dump.rdb`）。    | 快速恢复；适合全量备份。     | 配置周期性生成，可能丢失最近几分钟的数据。 |
| **AOF（追加文件）**    | 每次写操作追加到日志文件（`appendonly.aof`）。    | 数据更完整，可配置写入频率。 | 文件比 RDB 大，恢复较慢。                  |
| **混合持久化（默认）** | RDB + AOF（重写时使用 RDB 写入数据 + AOF 补充）。 | 兼顾启动速度和数据。         | 仍受写入频率和 fsync 策略影响。            |

**fsync****策略\****决定了** **AOF****的\****写入频率：**

- `always`：每次写操作都同步，最安全但最慢。
- `everysec`（默认）：每秒同步一次，性能与可靠性平衡。
- `no`：由操作系统决定刷盘，性能好但数据不可靠。

此外，Redis 还支持主从复制和哨兵机制，在主节点宕机时由从节点接管，实现**高可用 + 容灾备份**。

### 如何选择 RDB 和 AOF？

| **方案**                  | **适用场景**                                       | **特点**                                                     |
| ------------------------- | -------------------------------------------------- | ------------------------------------------------------------ |
| **只用 RDB**              | 对数据一致性要求不高，追求恢复速度，例如缓存系统。 | 文件小，恢复快，但可能丢失数分钟数据。                       |
| **只用 AOF**              | 对数据完整性要求高，接受恢复速度慢，例如交易系统。 | 更安全，但文件大、恢复慢。                                   |
| **RDB + AOF（推荐）**     | 绝大多数生产环境                                   | 兼顾安全性和性能。RDB 负责快速恢复，AOF 确保数据完整性。     |
| **混合持久化（AOF重写）** | Redis 4.0 之后的默认选项，适用于大多数用户。       | 重写时以 RDB 为主，追加 AOF 写命令，兼得 RDB 和 AOF 的优势。 |

### Redis 大 key 对持久化有什么影响？

大 key（单个键值对很大，如几 MB 的字符串、Set 或 Hash）会严重影响 Redis 的持久化、复制、阻塞等方面：

| **影响方面**                  | **说明**                                                     |
| ----------------------------- | ------------------------------------------------------------ |
| **写时复制（Copy-On-Write）** | Redis 在后台重写 AOF 或 RDB 快照时使用 `fork()` 创建子进程，共享父进程内存。如果主进程修改了大 key，会触发写时复制，造成**大量物理内存拷贝**，甚至 OOM（内存不足）。 |
| **持久化时间延长**            | AOF 重写或 RDB 快照需遍历所有 key，大 key 会显著**拉长持久化耗时**，增加阻塞风险。 |
| **阻塞主线程**                | Redis 是单线程，大 key 的读取/写入操作会阻塞其他请求，尤其在执行命令如 `DEL`、`LRANGE` 时更明显。 |
| **主从同步缓慢**              | Redis 主从同步时会全量复制数据，大 key 会导致**主从复制慢或失败**。 |
| **重启恢复变慢**              | 启动时 AOF 文件加载大 key 会耗费大量时间。                   |

解决方法：

- 将大 key 拆分为多个小 key。
- 使用 `MEMORY USAGE key`命令排查大 key。
- 定期使用 `redis-cli --bigkeys`工具做大 key 分析。
- 避免使用 `hset myhash field value`向一个 hash 塞入上百万个字段。

## 缓存双写一致性

### Cache Aside 策略

#### 先更新数据库，再删除缓存

**优点：**

- 简单安全，**避免\****脏数据**。
- 删除缓存操作失败也不会导致数据库和缓存不一致（下次读会重新从 DB 加载）。

**缺点：**

- 在**高并发场景**下，可能出现 **脏读**问题（见说明）

没删除缓存前，另一个线程读取缓存

**加分布式锁：**

- 请求更新或读取数据时对 key 加锁；
- 更新完成再释放锁；
- 保证串行访问，强一致性。

#### 先删除缓存，再更新数据库

缺点：

- 更新数据库成功前，其他线程可能会请求刚被删除的缓存；
- 缓存 miss 后触发 **缓\****存回填**，将旧数据从数据库重新读入缓存；
- 导致**旧数据回写缓存**，缓存中数据被“污染”。

正确做法：

**延迟双删：**

```plain
updateDatabase(key, value);
redisTemplate.delete(key);
Thread.sleep(100); // 延迟一会儿
redisTemplate.delete(key); // 再次删除，确保缓存一致
```

### Redis 主从同步中的全量同步和增量同步如何实现？

全量同步触发时机：

- 从库第一次连接上主库
- 从库与主库断开连接时间过长，增量同步无法进行

实现：

1. **PSYNC****命令**：从库向主库发送 PSYNC ? -1 命令，表示请求全量同步。
2. **BGSAVE**：主库接收到命令后，会执行 BGSAVE 在后台生成一个 **RDB 快照文件**。
3. **缓冲区记录**：在生成 RDB 文件的**同时**，主库会开始将所有新的**写命令**记录到一个内存缓冲区中（这个缓冲区就是**复制积压缓冲区****repl_backlog** 的一部分）。
4. **发送 RDB 文件**：RDB 文件生成完毕后，主库将其发送给从库。
5. **从库加载 RDB**：从库接收到 RDB 文件后，会**清空自己所有旧的数据**，然后加载这个 RDB 文件，将自己的状态恢复到主库执行 BGSAVE 时的状态。
6. **发送增量命令**：RDB 加载完成后，主库再将之前**缓冲区中记录的所有写命令**发送给从库。
7. **从库执行增量命令**：从库执行这些命令，最终达到和主库完全一致的状态。

增量同步触发时机：

- 主从连接短暂断开

实现：

- 从库发送自己挤压缓冲区的偏移量
- 主库比较偏移量是否有效
- 无效则进行全量同步，有效则将后续所有命令发送给从库

`repl_backing(挤压缓冲区)` 环形缓冲区，旧值会被覆盖，只在主库存在。主从库维护各自的偏移量。主库记录生成发送，从库记录接收处理。

### 哨兵机制原理是什么？

1. **监控 (Monitoring)**：哨兵进程会持续地向主库和所有从库发送 PING 命令，检查它们是否存活。
2. **通知 (Notification)**：当某个 Redis 实例出现问题时，哨兵可以通过 API 通知系统管理员或其他应用程序。
3. **自动故障转移 (Automatic Failover)**：这是最核心的功能。当主库被判定为下线时，哨兵会自动在从库中选举出一个新的主库，并让其他从库去复制这个新主库。

原理：

哨兵集群、主观下线、客观下线、选举
